# Runtime Publishing, End-to-End from Local Plexus Authoring — a Live Environment Loop

**Program:** Environments → PPAC-analog Admin → Graphs/Solutions → Plexus. This is **Milestone-2, Stage 1**. Parent design: `docs/superpowers/specs/2026-10-20-environments-graphs-admin-design.md`. Milestone-1 (SP-GRAPH-1..5) built the whole author→contribute→promote→serve spine; this slice makes that spine *actually run* for the first time, driven by the real Plexus app, and closes the gaps that block a real run.

## Intent and why

Everything the loop needs has been written, typechecked, and diff-reviewed — but **it has never once executed**. Every milestone proof (`control-plane-smoke.ts`, `sp0-/sp1-capstone-e2e.test.ts`) is gated, none of them connects the *real* Plexus app to a runtime-served-and-read application, the richest one (`sp1-capstone`) is server-only with synthetic packages and tests only the per-app bind, and it even depends on a `pragmatic-server:sp1` image that has no build recipe. "It compiles and the diffs look right" is not "it works." This slice converts the program from built-and-believed to demonstrably-working: a person authors a simple solution in Plexus, publishes it, an admin promotes it, and a browser loads the served app and sees the promoted data — for real, on the user's Docker machine.

The milestone proof is a **read** of a **simple graph** — a small ontology modeled on Microsoft's Contoso and Northwind samples (a few concepts and representative seeded instances; see D5), not the full warehouse. Connectors, external data sources, and provisioned databases — including a *live* connection to the real Contoso/Northwind SQL databases — are explicitly Stage 2; here the data is authored into the graph and read from the promoted graph.

## Goals

- **G1 — Run the full environment loop for real.** Local Plexus authoring → contribute compiled packages to a Development environment graph → admin promote (dev→runtime) → publish an **environment-bound** app to the Runtime environment → the runtime serves the app → a browser loads it and reads the **promoted environment graph** live. On simple-graph data, with no connectors.
- **G2 — Prove it by driving the real Plexus Electron app with Playwright.** The e2e launches the actual Plexus application and drives the real New Project / Generate UI / Configure / Contribute / Publish UI, not server-side synthetic builders. A real chromium browser loads the served app and asserts the promoted data is visible. **Hard constraint: every on-screen window the e2e spawns (the Plexus Electron window and the chromium browser) must open on the operator's second monitor** so a real run never takes over the primary display.
- **G3 — Close the gaps that block a real run** (enumerated below): a committed sample solution; control-plane runtime containers started so a browser can load the served app; a working runtime read-grant in the loop; token/identity provisioning the harness can perform; and an operator runbook for the one-time manual prerequisites (image build, control-plane start).
- **G4 — First real exercise of the SP-GRAPH-5 environment-bound path.** `tenant.publish-env` + the no-`OpenApplication` env-graph read has zero end-to-end coverage today; this slice is its first real run.

## Non-goals (Stage 2 or later; filed as deferred Features)

- **Connectors, external data sources, provisioned databases (Postgres).** The entire Stage 2. The loop here reads the in-graph promoted data only.
- **Thin-client / remote multi-user dev authoring** (the former SP-GRAPH-6: Plexus authoring *over the wire* against a dev environment, with a server-side build). Deferred; the grounding from this conversation is preserved. Development stays **local** — author locally, ship a snapshot of compiled packages.
- **Promote inside Plexus.** The dev→runtime promote remains an admin/control-plane action (Decision D4; the user may override).
- **A login / token-mint flow inside Plexus.** The maker still pastes a URL + pre-minted token into the Configure dialog (the harness mints and injects them). A product sign-in flow is later work.
- **Portal UI for `app-reader-grant`, CSP / X-Frame-Options hardening on the served shell, the `CypherAppDeployParamsDto` rename.** Already-filed deferrals; not reopened here.
- **Per-app bundled publish as the milestone.** The per-app path works today and is the existing harnesses' subject; it is a useful smoke but does not exercise environments/promotion and is not the Stage-1 proof.

## Anti-goals (these would make the slice a failure even if green)

- **Weakening a security gate to make the read pass.** The served app's principal must read the promoted graph by holding a *real* read grant (`Viewer` → `Action.Read` through the `readTenant` gate). A principal with no grant must still be denied. Do not loosen `policy-gate` or the env-graph read path.
- **A proof that bypasses the real app.** Building packages from a synthetic in-process TODL `Repository` (as `control-plane-smoke`/`sp1-capstone` do) does **not** satisfy G2. The packages and the deployed app must come from the real Plexus build pipeline driven through its UI.
- **Any secret in a log, DTO, error, or the renderer.** Owner credentials, maker/admin/deploy tokens, passwords, and `modelJson` content never get logged, echoed, returned in a DTO, put in an error message, or crossed to the renderer. (Program-wide discipline; re-verified here because the harness handles tokens.)
- **Silently expanding Plexus's product surface.** Add only what the loop needs to run; no new maker features beyond that.

## The loop, concretely (what Stage 1 wires and runs)

Numbered by where each step runs. "CP" = control plane (`admin/control-plane/`, operator-authenticated HTTP on `127.0.0.1:7000`). "Plexus" = the real Electron app driven by Playwright. "Server" = a `pragmatic-server:dev` container the CP creates per environment.

1. **(operator, one-time)** Build the `pragmatic-server:dev` image, with Docker running and a Playwright chromium installed. That is the whole manual prerequisite (documented in the runbook, G3). The control plane is **not** started as a separate process — the e2e composes `ControlPlaneHost` **in-process** (as `control-plane-smoke.ts` does) and owns env creation/teardown; the admin portal is not needed (the harness drives the CP directly, not its UI).
2. **(CP, scripted by the harness)** Create a **Development** environment (`POST /api/environments {type:"development", template:"dev-blank"}`), create a graph in it (`POST .../graphs`), and mint a **maker token** (`POST .../maker-token`).
3. **(Plexus)** New **Architecture** project seeded from the committed sample solution → **Generate UI** → **Configure graph server** (paste the dev env's WS URL + maker token) → **Contribute to graph**. This sends the solution's compiled packages into the dev environment's graph via `GraphProtocol.Contribute` (gated `EnsureDevelopment`).
4. **(CP, scripted)** Create a **Runtime** environment (`type:"runtime"`, `template:"demo-contoso"`, tenant `contoso` — mirrors `control-plane-smoke`, which gives the runtime a provisioned admin to deploy against), then **promote** the dev graph into it (`POST /api/environments/<dev>/graphs/<g>/promote {targetEnv:<runtime>}`). The runtime's one environment graph now holds the promoted data. The harness then creates the **read principal as a real credentialed `Viewer` account** on the runtime tenant (`AdminProtocol.CreateAccount` + `GrantRole Viewer Tenant`, as the smoke's `env-reader` does) and a second **ungranted** account for the deny proof.
5. **(Plexus)** **Configure tenant** (paste the runtime env's URL + a deploy token derived from the runtime env's provisioned admin credential, which the in-process CP harness reads from the env's `provisioned-secrets.json` — no new CP route needed) → **Publish (environment graph)** (`tenant.publish-env`, `RemoteBindMode.Environment`). This builds `html-bundle-remote` in environment-bind mode and `DeployApplication`s it to the runtime (gated `EnsureRuntime`); the app's generated client reads with **no** `OpenApplication`, so reads fall through to the environment graph.
6. **(chromium)** Browser logs in as the credentialed `Viewer` reader account (`POST /auth/browser-login?tenant=contoso` with that account's email + password) and loads `http://localhost:<rtPort>/app/contoso/<app>/`; the test asserts the **promoted data** is rendered. For this to work the runtime container must be started with an allowed origin (gap fix, G3).
7. **(assertions, per Review Focus)** env-bound read *before* promote surfaces `NoEnvironmentGraphError` cleanly; a principal with no grant is denied; a **re-promote** is reflected on the next read with no redeploy.

## The gap list this slice closes (grounded, with evidence)

Blocking a real run today — each is in scope for Stage 1 unless marked:

1. **No committed sample solution.** No `.todl` fixture exists in either repo outside `node_modules`/`dist`; harnesses rely on an un-committed `C:/tmp/sp1-smoke/project` or server-side in-process builders. → **Add two committed Architecture sample solutions** — Contoso and Northwind ontologies, each with a simple reader app and representative seeded instances (D5) — as the e2e subjects.
2. **Control-plane runtime containers can't be browser-served.** `DockerEnv.RunArgs` (`environments/seed/docker.ts:99-117`) never sets `PRAGMATIC_ALLOWED_ORIGINS`, so a browser loading `/app/...` fails the origin check; the sp0/sp1 e2e only worked because they set it on their own `docker run`. → **Set an allowed origin on control-plane-created runtime containers** (at minimum for runtime envs that serve apps).
3. **The runtime read principal needs a *credential* the browser can log in with.** `app-reader-grant` / `AdminGrantAppReader` (`environment-service.ts:316`) grants `Viewer` to a **credential-less** well-known principal `app-reader`; there is no account/password for it, and `/auth/browser-login` needs `{email,password}`, so a browser can never authenticate *as* `app-reader`. → **This slice does not use `app-reader-grant`.** The loop's reader is a real credentialed `Viewer` account the harness creates (`CreateAccount` + `GrantRole`, mirroring the smoke's `env-reader`); that satisfies the "real grant, not an open door" proof via the browser. `app-reader-grant` stays built-but-unwired and **remains deferred** (its serve-time machine-principal auth is a separate, later concern).
4. **The env-bound (SP-GRAPH-5) path has zero e2e coverage.** Both capstone and plexus-smoke use `Application` bind; the `Environment` branch (`publish-tenant-contributor.ts:90`) is unit-tested only. → Covered by G1/G4 directly.
5. **No automated entry point connecting real Plexus to the loop; it has never run.** The only Plexus e2e (`apps/plexus/e2e/sp1-plexus-smoke.spec.ts`) is gated `SP1_SMOKE=1`, uses `Application` bind, defers served-app verification, and calls itself "not a product test." → **Build the Stage-1 Playwright e2e** that drives the real app through contribute + publish-env and asserts the browser read.
6. **Token/identity provisioning is manual and external.** Plexus has no login/mint flow; a fresh tenant denies reads until a grant exists. → **The in-process CP harness mints the maker token (CP `maker-token` route) for contribute, reads the runtime env's provisioned admin credential from its `provisioned-secrets.json` (as `control-plane-smoke` does) to obtain a deploy token for publish-env, and creates the credentialed `Viewer` reader + an ungranted account for the deny proof.** The URL + tokens are injected into Plexus via the real Configure dialogs. No secret is logged; tokens go only into Plexus's encrypted main-side profile store. (No net-new CP route to mint a runtime deploy token is required — the in-process harness has filesystem access to the shared `dataRoot`.)
7. **Operator prerequisite is unscripted** (building the `pragmatic-server:dev` image needs Docker + BuildKit + a private `.npmrc` `read:packages` token). → **Documented in a runbook**, run once by the operator; not automated by the test. The control plane and portal are *not* separate prerequisites — the e2e composes the CP in-process; the master key and env bundles are managed by that in-process CP exactly as the smoke already does.

Not closed here (confirmed out of scope): single-box Postgres (Stage 2); sp0/sp1 image recipes (we use `:dev` via the control plane, not `:sp0`/`:sp1`); cluster/mTLS bring-up.

## Decisions already made (the "how", as decided)

- **D1 — Reach: the full environment loop.** (User.) Contribute → promote → env-bound publish → env-graph live read. Per-app bundled publish is not the proof.
- **D2 — Proof: the real Plexus Electron app via Playwright + chromium.** (User.) The build and the deployed app come from the real Plexus pipeline driven through its UI; a real browser asserts the read.
- **D3 — Orchestrated through the control plane, on the `pragmatic-server:dev` image.** The full loop needs *two typed* environments (a Development to contribute+promote from, a Runtime to publish+serve) and the promote route — only the control plane provides typed envs and promote. Single-box `docker-compose` (one untyped server) is insufficient. The e2e **composes the control-plane host in-process** (as `control-plane-smoke.ts` does) rather than starting it as a separate operator process — this gives the harness filesystem access to the shared `dataRoot` for provisioned credentials and keeps env creation/teardown deterministic. The runtime environment uses the `demo-contoso` template (tenant `contoso`), which ships a provisioned admin to deploy against; the development environment uses `dev-blank`. (My call.)
- **D4 — Promote stays an admin/control-plane action**, driven by the harness as a scripted call on the in-process control-plane host between the two Plexus actions — not a new Plexus feature. (My default call; the user may override to pull promote into Plexus.)
- **D5 — Sample content: two committed sample solutions modeled on Microsoft's Contoso and Northwind.** Each is an **ontology** (TODL concepts) plus a **simple reader app** (a model that reads the graph and displays it meaningfully): Contoso as a retail-sales ontology (`Product`/`Customer`/`Store`/`Sale`) with a product-catalog + sales view; Northwind as an orders ontology (`Product`/`Category`/`Customer`/`Order`) with an equivalent view. Each is a representative *simple* subset, not the full schema. Data is **authored as instances into the graph** and read from the *promoted* graph; a live connection to the real Contoso/Northwind SQL databases is a connector and stays Stage 2. **Contoso is the primary e2e subject that drives the asserted browser read** — the `demo-contoso` runtime tenant seeds Northwind as its own demo data, so promoting Contoso keeps the asserted (promoted) data visibly distinct from anything the tenant seeds. The second solution ships alongside to show the loop generalizes (optionally a second e2e pass). The test opens a committed solution and drives Generate-UI / Configure / Contribute / Publish through the real UI; solution *content* is the committed fixture (not typed char-by-char), all *actions* go through the UI. (Contoso/Northwind choice: user. In-graph-not-connector, the simple-subset shaping, and Contoso-as-primary: my calls.)
- **D6 — Identity: harness-provisioned, real credentialed grants.** Maker token via CP `maker-token` (contribute); deploy token from the runtime env's provisioned admin credential read off `provisioned-secrets.json` (publish-env); the browser reader is a real **credentialed `Viewer` account** created via `CreateAccount` + `GrantRole` (mirroring the smoke's `env-reader`), plus a second ungranted account for the deny proof. The browser authenticates via `/auth/browser-login`. `app-reader-grant` is **not** used (its principal is credential-less; see gap-3) and stays deferred. No gate weakening. (My call, within the user's "full loop" decision.)
- **D7 — Repos touched (build order):** `pragmatic-server` (control-plane allowed-origin fix; the in-process CP orchestration + credentialed-reader provisioning the e2e needs; runbook) → `Plexus` (the Playwright e2e harness; the committed sample solution; any small publish/contribute fix the real run surfaces). TODL/protocol only if the real run exposes a genuine gap (prefer reuse). In-place feature branches per repo (NOT worktrees — npm install over a worktree detaches sibling symlinks); rebuild each sibling's `dist` before dependents resolve it.

## What's left to the builder

- The Playwright harness file layout and the exact selectors/flows for New Project, Generate UI, the Configure dialogs, Contribute, and Publish-env; Electron launch wiring (extend the `sp1-plexus-smoke.spec.ts` pattern, which already launches the real app and drives the real service objects).
- Each sample solution's exact content (concepts/model/data) and the display shape of each reader app; data values chosen so the browser read asserts an unambiguous *promoted* value, kept distinct from any data the runtime tenant seeds (default: Contoso drives the asserted read — see D5).
- How tokens are injected (drive the real Configure dialog vs. pre-seed the encrypted profile store) — within D6, whichever is robust in a headless Electron + Playwright run, never logging the secret.
- The in-process control-plane orchestration (`ControlPlaneHost`: create-env / create-graph / maker-token / create-runtime / promote) and how the test obtains the per-env container ports (from the environment service, as the smoke does) and reads the runtime env's provisioned admin credential from `provisioned-secrets.json`.
- Gating: the e2e is operator-run (needs Docker + a built `:dev` image + chromium), gated by an env flag like `SP_RUNTIME_LOOP_E2E=1`, consistent with the program's existing gating posture. Unit/typecheck suites stay green and unconditional.
- The exact mechanism and placement of the allowed-origin fix (which env types/containers get it, and its default value) within D3/gap-2.
- Second-monitor window placement (G2): position both the launched Plexus Electron window and the Playwright chromium window on the operator's second monitor — detect the second display's bounds (Electron `screen.getAllDisplays()` for the app; a `--window-position=<x>,<y>` launch arg for chromium) with a configurable origin env var (e.g. `SP_E2E_WINDOW_ORIGIN="<x>,<y>"`) as the override, since the monitor arrangement is machine-specific.

## Review focus (failure modes no single happy-path step exercises)

- **Env-bound read before anything is promoted** → the clear `NoEnvironmentGraphError` surfaces to the client (not a crash or blank page).
- **A runtime principal with no read grant** → denied; the granted reader holds a real `Viewer` grant, not an open door (prove both the granted-reads case with the `Viewer` account and the ungranted-denied case with the second account).
- **Re-promote under a running app** → the already-served app's next read reflects the new graph, with no redeploy (shared live instance).
- **Browser origin / cookie correctness** → the served shell loads only with the allowed origin set and a valid `browser-login` session; a wrong origin is refused.
- **Secret hygiene** → maker/admin/deploy tokens and passwords never appear in logs, test output, DTOs, errors, or the renderer; `modelJson` content is never echoed.
- **Container lifecycle** → envs/containers created by the harness are torn down (or clearly left for inspection) deterministically, so a re-run starts clean.

## Exit criteria

- The Stage-1 Playwright e2e, run on an operator machine with Docker + a built `:dev` image + chromium, drives the real Plexus app through contribute → (scripted promote) → publish-env, and a real browser asserts the promoted simple-graph data is served and read live — green.
- The Review-focus cases above are each asserted.
- All repos' unit suites and typechecks remain green; no security gate weakened; no secret surfaced.
- A runbook documents the one-time operator prerequisites and how to run the e2e.
