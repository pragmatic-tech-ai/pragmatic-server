# Plexus sign-in to an in-hive tenant console - design

Status: draft for approval (2026-11-04). Follows docs/superpowers/specs/2026-11-04-plexus-sign-in-publishing-design.md,
whose follow-up list names "Desktop API + relay on the in-hive tenant console".

## Intent

Some tenants run their console inside the client's own cluster (the in-hive tenant console, `tenant-admin-server.ts`),
not on the control plane's tenant plane. People in such a tenant should sign in to Plexus with their email exactly as
everyone else does, and contribute / publish to their environments, with the same guarantees as the control-plane path:
no address, token or password reaches Plexus; the console mints a short-lived, narrowly scoped credential per relay;
sign-out, password change, Owner reset and tenant delete end access.

## Decided by the user

- **Finding the console: both.** The control plane's email lookup returns the in-hive console's address when it knows
  it; Plexus also offers a typed console address as a fallback for hives that never share it.
- **Exposure: an Ingress on a client-chosen host.** The hive install gets an Ingress for the console, like the IdP and
  environments already have. Browsers and Plexus use that address.
- **Matching an email to a tenant: fingerprints and email domains.** The hive sends one-way fingerprints of its account
  emails when it dials home; the control plane never holds the addresses. Tenants may also declare email domains; an
  email on a declared domain goes to that tenant's console. Exact fingerprint matches come first.

## Goals

1. An in-hive console serves the desktop API (`/desktop/*`) and the relay (`/desktop/relay`), composed from the same
   `tenant-auth/desktop-*` classes the control plane uses.
2. The console reaches its environments over in-cluster Service DNS (the `record.endpoint` already stored for in-cluster
   environments), never `kubectl port-forward`.
3. The console is reachable through an Ingress on a host the operator sets at hive install.
4. The console periodically tells the control plane its public address and its account-email fingerprints over the agent
   channel; the control plane's discovery uses them.
5. Tenants can declare email domains (operator in the platform admin portal; Owner in the tenant console). Discovery
   matches by fingerprint, then by domain, then the existing control-plane index.
6. Discovery answers carry a per-tenant console address; Plexus signs in against the address of the tenant chosen.
7. Plexus's account dialog has an "Use a specific console address" option; the typed address is remembered.

## Non-goals

- Changing the control-plane path that works today.
- Moving account data out of the hive. Only the console address and fingerprints leave it.
- Finer roles or per-environment grants (still a later follow-up).

## Prerequisite found while surveying (now in scope, see below)

The in-hive console cannot manage in-cluster environments today: its `EnvironmentService` uses `HiveOrchestratorFactory`,
which needs a kubectl context, and the console pod has no kubectl, no ServiceAccount token
(`automountServiceAccountToken: false`) and no RBAC. So there are no environments for its relay to reach yet. The relay
also needs each environment's admin secret (`<env>-env-secrets`), which today is read with kubectl.

## How it works (builder's guide)

### Console exposure
`K8sManifestBuilder.RenderTenantAdmin` gains a TLS-terminating Ingress (shape of `ServerIngress`: class nginx, plain-HTTP backend to the console Service and port) on host `console-<tenant>.<baseDomain>` unless the
operator sets an explicit host at install, with the TLS choice described under "Decided by the user after the builder
check". Emitted only when a base domain or explicit host is set. The console's
`TenantHostResolver` accepts that host. The desktop routes stay Host-independent.

### Console advert over the agent channel
New agent-channel route `POST /agent/hives/:hive/console`, same bearer as the other routes, body
`{ consoleUrl: string, fingerprints: string[] }`, size-capped, validated (https URL; fingerprints are fixed-length hex;
count capped). The console posts it at start and every 5 minutes, and immediately after an account is created, deleted or
has its email changed. The control plane stores the latest advert per hive (new record store, replacing, never
accumulating) with `reportedAt`. A hive bound to several tenants is out of scope; a console serves one tenant.

Fingerprint = HMAC-SHA256(key, normalised email), normalised as `TenantAccountIndex.Normalise` does (trim, lowercase).
The key is per hive, generated by the control plane at bootstrap, stored encrypted with the master key on the control
plane and delivered to the console in its bootstrap Secret. A leaked advert file alone does not reveal emails; the control
plane itself can test a guess (it must, to answer lookups) - accepted.

### Email domains
`TenantRecord.emailDomains?: string[]` (lowercase, validated host names; public mail domains on a fixed deny list such as
gmail.com, outlook.com are refused). Editable by the operator (platform admin portal tenant detail) and by the tenant
Owner (tenant console settings; an in-hive console sends its list in the advert as `emailDomains`, and the advert is the
source of truth for in-hive tenants). A domain counts in discovery only once an operator approved it (decision D5 below):
domains the operator saves are approved on save, domains the Owner sets in either console wait for approval.

### Discovery
`DesktopDiscoveryEndpoint` resolves an email to tenants in order: fingerprint matches across adverts; else domain
matches; else the existing `TenantAccountIndex`. The 200 body keeps `tenantPlaneUrl` (unchanged) and each tenant entry
gains `consoleUrl` (the advert's address for in-hive tenants, the control plane's tenant plane otherwise). A tenant whose
advert is older than 24 h is still returned with its last address. Throttling, Origin refusal and status codes unchanged.

### Plexus
`DesktopApiClient` reads `consoleUrl` per tenant (falling back to `tenantPlaneUrl`) and stores the chosen tenant's address
in the desktop session, so every later call (targets, relay, sign-out) goes to that console. The account dialog gains a
"Use a specific console address" link: an https (or loopback http) address field; Plexus then calls that console's
`/desktop/sign-in/begin` directly with the email (a new console-side lookup answers which tenant the console serves).
The address is remembered in the account settings. Errors use plain sentences, as today.

### In-hive desktop API and relay
`TenantAdminServer.Compose` passes `withDesktop = true` and a `DesktopRelayWiring`. `EnvironmentEndpoints` gets an
interface; the console's implementation returns `record.endpoint` directly (no lease to hold) and reads the admin secret
through the prerequisite's in-cluster access. The desktop audit file lives in the console's data root. The console
registers the `pragmatic-desktop` OIDC client on its injected IdP exactly as the control plane does (loopback redirect
already supported).

## Left to the builder
File and class names, advert interval constants, the advert store shape, how the console learns account changes
(signal from its account service), test layout, and the portal UI details for email domains.

## Decided by the user after the builder check

- **A real console install is in scope.** The operator turns on "run the tenant console in this hive" on a hive in the
  platform admin portal and sets its host and certificate. The control plane then generates the console's Secrets
  (agent token, fingerprint key, IdP wiring) and the install is delivered with the hive's bootstrap bundle /
  `HiveAgentInstaller` path (today only the hive agent goes there; `TenantAdminBootstrap.GenerateBootstrap` is only
  used by smoke tests and becomes the production renderer). The portal shows install status from the console's first
  advert ("waiting for the console to report" until then).
- **In-hive environment management is in scope.** The console pod gets its own ServiceAccount (token mounted) with a
  ClusterRole allowing only create/get/delete of Namespaces named `pragmatic-env-*` (enforced in the console too, since
  RBAC cannot match name prefixes), and a RoleBinding to a namespaced Role with full rights inside each environment
  namespace it creates (created right after the namespace). It drives Kubernetes through the in-cluster API (a new
  orchestrator implementation behind the existing orchestrator interface, picked for `Local`/in-cluster hives when the
  process runs in a pod) instead of kubectl. The admin secret `<env>-env-secrets` is read through the same API.
- **TLS: both.** At install the operator names either an existing TLS Secret or a cert-manager issuer (then the
  Ingress carries the cert-manager annotation and a generated Secret name). The same choice applies to the IdP and
  environment Ingresses the console creates. Plexus uses normal system trust.
- **Development certificates (user, at approval).** A third TLS choice, "development self-signed", generates and
  installs certificates for a dev machine: the control plane creates a development CA once (kept in its data root,
  key encrypted with the master key), issues a certificate for each Ingress host it needs (console, IdP, environments;
  wildcard `*.<baseDomain>` where possible), and creates the TLS Secret in the cluster. A dev script installs that CA
  into the current Windows user's trusted roots (Windows shows its own confirmation) and can remove it again. Plexus's
  main process must use the system trust store for its HTTPS calls (Electron `net.fetch` or Node's system-CA option),
  so a CA installed that way is trusted without a Plexus-specific CA setting. The portal labels this choice as
  development only.

## My calls (from the builder check)

- **Discovery merges the tiers.** Fingerprint, domain and index matches are unioned and deduplicated per tenant. A
  tenant whose hive is set to run the console in-hive is left out of discovery until its first advert arrives, so the
  Owner's backfilled index entry never sends them to the control plane's tenant plane.
- **One console per tenant.** The control plane refuses turning on the in-hive console for a second hive of the same
  tenant. The advert store is keyed per tenant (recording the hive it came from).
- **Email domains for in-hive tenants come only from the advert.** The platform admin portal shows them read-only for
  those tenants; it edits them only for control-plane tenants.

## Accepted deviations and rulings (implementation)

- **The console reuses the hive agent token.** The control plane does not generate a separate token for the console:
  the console install requires the hive agent to be installed first and mounts the agent's own token Secret. The agent
  objects are not re-applied by the console install, so the running agent is never reverted.
- **Environment rights are a ClusterRole bound per namespace.** Instead of a namespaced Role, the console's environment
  rights are a ClusterRole that the console binds itself, with a RoleBinding in each environment namespace it creates.
  For that it holds cluster-wide `create` on rolebindings and `bind` on that one ClusterRole. RBAC cannot fence namespace
  name prefixes, so RBAC alone would let a stolen console token bind those rights in any namespace (pragmatic-system
  included). The fence is the console's own guard plus the admission policy below; the residual privilege is noted in the
  console ClusterRole's doc comment.
- **An admission policy fences the console server-side.** Each console gets a ValidatingAdmissionPolicy and binding
  (Kubernetes 1.30 or newer). It limits the console's service account to creating and deleting Namespaces named
  `pragmatic-env-*` that carry this hive's label, and to creating only the console environment RoleBinding (fixed name,
  console environment ClusterRole, console service account). The console's guard alone is client-side; the policy is what
  the API server enforces.
- **Environment namespaces enforce Pod Security `baseline`.** Every environment namespace carries the `baseline` enforce
  label, and the console's admission policy requires `baseline` or `restricted` on any namespace the console creates, so a
  stolen console token cannot run privileged pods (node root). Environment workloads must stay baseline-compliant.
- **Hive delete removes the console and its environment namespaces.** Deleting a hive removes its console objects
  (cluster-scoped grants and admission policy included, also for bootstrap installs) and every Namespace that carries the
  hive's label and is named `pragmatic-env-*`; an unlabelled `pragmatic-env-*` namespace is never touched. Namespaces that
  cannot be deleted are reported to the operator as failed. A delete anyway skips the cluster entirely.
- **An operator approves each email domain a tenant Owner sets (user, Plan 2 pre-flight D5; extended to control-plane
  tenants at the final review).** Nothing proves that a tenant owns the domains it claims: an in-hive tenant's Owner (or
  anyone holding the hive agent token the console reuses), and equally a control-plane tenant's Owner on the tenant plane,
  could claim another company's domain and have discovery send those people to their console. So a claimed domain takes
  effect in discovery only after an operator approves it once in the platform admin portal (tenant detail page: each
  claimed domain with approved yes/no and the other tenants that claim it; approve and revoke actions, operator Full only,
  audited with the domain). A tenant's claimed domains are its console advert's (in-hive) or its record's (control-plane).
  Domains the operator saves for a control-plane tenant (`PUT /api/tenants/:id/email-domains`) are approved on save; those
  the Owner sets (`PUT /tenant-api/settings/email-domains` in either console) wait, and the tenant console names the ones
  still pending. Approvals are stored per tenant in one store on the control plane (`console-domain-approvals.json`), apart
  from the advert store and the record, so they survive re-adverts and Owner edits; discovery's domain tier for every
  tenant is its claimed domains that are also approved, so a domain dropped from the advert or record stops matching even
  if it stays approved. Such an approved but no longer claimed domain stays listed (marked no longer claimed) so the
  operator can revoke it before a later claim re-arms it. Approving a domain the tenant does not claim is refused; revoke
  accepts any well-formed domain name (so an approval the policy has since come to refuse can be cleared). Approvals are
  forgotten with the tenant. Routes: `GET /api/tenants/:id/email-domains`, `POST .../email-domains/approve` and
  `POST .../email-domains/revoke` with `{ domain }`.
- **Residual: account fingerprints stay unverified.** Fingerprints in an advert take effect without approval, so a console
  can claim fingerprints of any email address it computes with its hive's key. This only matches someone who types exactly
  that email address in Plexus, and discovery shows that tenant by name before anything else happens. Accepted.
- **A former in-hive tenant's record domains return after console removal.** While a hive runs the console, the tenant's
  record domains are ignored and the advert's domains are never copied back into the record (a hive must not write platform
  records). Once the console is removed and its advert forgotten, the record's old domains (the ones seeded into the
  console at install) are claimed again (and count where approved). The Owner's in-hive edits are not lost: the control
  plane ignores them until the console is reinstalled, but they stay in `email-domains.json` on the console's retained data
  volume, so a reinstall brings them back in its first advert (domains an operator approved before match again at once,
  since approvals are kept per tenant). Accepted.
